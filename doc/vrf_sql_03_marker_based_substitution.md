# VRF SQL 생성 방식 3) 명시적 마커 기반 치환(형태 유지 + 안정적 삽입)

대상 코드: app/gen_vrf_sql_markers.py
템플릿 파일: app/vrf_template_markers.sql

## 1. 개요
마커 기반 치환은 “템플릿 기반의 장점(형태 유지)”과 “정적 생성의 안정성(정확한 삽입)”을 결합한 방식입니다.

핵심 아이디어:
- SQL 골격/주석/레이아웃은 템플릿 파일이 **그대로 보유**
- 파이썬은 템플릿 내부의 **명시적 마커(정해진 위치)** 에만 텍스트를 삽입하거나 삭제
- 마커가 예상과 다르면(예: 0개, 2개) **즉시 에러**를 내어 잘못된 결과 생성(조용한 실패)을 막음

## 2. 템플릿 설계
### 2.1 스칼라 placeholder
- `{{name}}` 형태로 넣고, 파이썬이 문자열 치환합니다.
- 예: `{{v_stat_dt}}`, `{{table_ref}}`

### 2.2 명시적 마커(블록 삽입 지점)
템플릿에는 다음 3개 마커가 들어갑니다.

1) 라인 마커: `--__METRICS_SELECT__`
- 해당 “한 줄 전체”를 메트릭 SELECT 라인들로 치환
- 메트릭이 없으면 마커 라인을 제거

2) 라인 마커: `--__WHERE_CLAUSE__`
- 해당 “한 줄 전체”를 WHERE/AND 라인들로 치환
- 필터가 없으면 마커 라인을 제거

3) 인라인 마커: `--__METRICS_STRUCT__`
- `FILTER_COUNT AS FILTER_CNT--__METRICS_STRUCT__` 처럼 **같은 줄 내부**에 존재
- 메트릭이 있으면 `,\n    STRUCT(...) AS METRICS`를 붙임
- 메트릭이 없으면 빈 문자열로 제거

## 3. 안전장치(정확한 삽입 보장)
마커 기반 구현의 중요한 특징은 **검증(guardrail)** 입니다.

- 라인 마커는 템플릿에서 **정확히 1번만** 존재해야 함
  - 아니면 `ValueError` 발생
- 인라인 마커도 `count() == 1`을 강제

이렇게 하면 템플릿이 수정되어도 “잘못된 위치에 끼워 넣고 조용히 결과가 깨지는 상황”을 줄일 수 있습니다.

## 4. 요구사항 매핑(20260225)
`app/table.ini`의 플래그/컬럼 값에 따라 **삽입할 텍스트 자체를 생성**하고, 마커 위치에만 주입합니다.

- `v_use_yn!=Y`: 해당 로우는 파일 생성 자체를 스킵
- `v_metric_sum_yn=Y`: `v_sum_col1/2` 값이 있는 것만 `SUM()` 라인 생성
- `v_metric_cnt_yn=Y`: `v_cnt_col1/2` 값이 있는 것만 `COUNT(DISTINCT)` 라인 생성
- `v_filter_yn=Y`: `v_filter_col1/2` 값이 있는 것만 `WHERE/AND` 라인 생성

## 5. 장점/단점
### 장점
- **형태 유지 극대화**: 템플릿이 곧 최종 결과의 기본 형태
- **정확한 삽입**: 마커 위치 외에는 변경하지 않음
- **템플릿 변경 내성**: 템플릿이 바뀌어도 마커만 유지되면 코드 수정이 거의 없음
- **실패가 빠름**: 마커 누락/중복 시 즉시 에러

### 단점
- **템플릿 작성 규율 필요**: 마커를 반드시 유지해야 함
- **마커 설계가 필요**: 어떤 블록을 유연하게 바꿀지(메트릭/필터/JSON 구조 등) 미리 결정해야 함

## 6. 언제 이 방식을 선택하는가
- SQL 골격/주석/레이아웃을 템플릿에서 엄격히 유지하고 싶고
- 삽입/삭제할 구간이 명확하며
- “조용한 실패”를 최대한 피하고(마커 검증)
- 템플릿 수정이 잦을 가능성이 있을 때

## 7. 실행 방법
- `python3 app/gen_vrf_sql_markers.py`

옵션:
- `--template app/vrf_template_markers.sql`
- `--table app/table.ini`
- `--out app/out`
